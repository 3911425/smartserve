# 项目发展路线：当前优化到秋招

更新：2026-10-23 · 当前基线 `2.1-20261023`。先优化当前项目→吃透代码→寒假实习→二次优化→三次优化→暑期投递→秋招；阶段顺序保留，未来功能不写成已实现。

## 总原则

主线保持“AI客服解决业务问题”。当前阶段一次有边界的大优化，然后冻结功能、理解源码；实习稳定后依据失败数据做二次优化；暑期实习投递前完成部署和质量闭环；秋招前用真实运行证据替代口号。阶段按能力验收推进，不因为某一天到了就机械加架构。

“达到大厂项目水平”不是一个可认证的功能列表，更不能保证某公司offer。可控目标是：能独立实现和调试关键链路，证明设计取舍和结果，承认边界，并通过足够的算法/基础训练与模拟面试。

## 阶段一：当前版本，冬实习前的一次优化

这一版的核心已经收敛为：真实账户权限、模拟交易闭环、受限自主Agent、可靠任务与追踪、可复现评测和学习资料。暂不加微服务、评论推荐、多模态或更多中间件。

当前已经完成：登录/注册及后端身份、模拟钱包与购买、三场景随机配送、统一售后资格、退款确认/撤回/重提/版本历史、工单幂等和权限、前后端业务版本检查、源码构建签名、两套PG回归及三种启动验证。它们是这一轮的现状，不再重复列为二次优化计划；完整证据与仍未验证的边界见[验证报告](06-评测与验证报告.md)。

完成标准：

1. 客户注册→购买并观察随机场景→需要时管理员顺序推进→售后确认/撤回/重提→管理员审核→钱包及申请历史全程可解释。
2. 能画出一笔购买的事务边界、锁顺序、唯一约束、失败回滚和幂等重试。
3. 能区分主管路由、领域自主循环、确定性订单节点，逐次计算模型调用。
4. 能从文档加载追到BGE向量、候选排序、accepted、模型上下文和最终引用。
5. 能复现实测报告中的一个失败案例，提出可验证修复，而非只背框架定义。
6. 能在陌生机器说明本机/混合/全容器三种启动、额外H2试用、数据卷和端口，解释同规则与同数据的区别。

这一阶段的退出条件是正确性回归通过、文档能对应源码、核心链路能独立调试；完整在线Agent质量集、压测、公开上线和备份恢复演练仍是后续工作，不能因已有烟雾测试就宣布完成。

## 阶段二：吃透代码，冻结功能2至4周的参考安排

时间是建议，可按课程调整。第一周账户/交易/SQL；第二周Agent/MCP/图与恢复；第三周RAG/评测/失败分析；第四周故障演练和模拟面试。每天保留算法与Java基础训练，不能把全部时间交给读项目。

产出每周一张自己画的链路图、一个可复现问题记录、一个独立修改及回归、一次15分钟讲解录音。通过学习手册验收再进入新功能。读过文件、看懂AI解释、能复制启动命令，都不等于已经掌握。

允许修缺陷和补必要测试，避免不断重写主架构。把新增想法放待办，除非影响正确性或阻碍理解，否则留到二次优化。

## 阶段三：冬实习期间，先稳定工作与基本功

实习前期重心是团队工程实践：代码审查、线上排障、需求拆解、测试、SQL与性能，涉及公司代码或数据不得带回个人项目。每周给个人项目留一个小复盘时段，记录“当前设计在什么条件下会失效”，不急着迁移公司架构。

进入二次优化的条件：实习节奏稳定，能够独立维护当前项目，明确2至3个有证据的瓶颈。若只是觉得技术不够多，不构成重构理由。

## 阶段四：二次优化，优先质量与工程稳定性

| 优先级 | 内容                                                  | 需要交付的证据                                     |
| ------ | ----------------------------------------------------- | -------------------------------------------------- |
| P0     | 专家/人工复核高价值评测集，真正未参与调参的保留集     | 标注规范、分歧处理、版本化数据、分组结果           |
| P0     | 当前TokenDance模型完整在线回归；Agent澄清、复合意图、预算、注入、故障 | 独立标注的任务成功率、失败归因、成本/延迟分布；不复用旧模型成绩 |
| P0     | RAG索引发布、过滤、重排策略的可验证改进               | 增大语料、消融实验、Recall/MRR/误接受、具体失败    |
| P1     | 后台任务和事件清理、全局限流、多实例租约验证          | 崩溃/重投/失效演练，无法保证的部分明确记录         |
| P1     | 上线准备：HTTPS、访问隔离、密钥管理、备份恢复         | 可重复部署和恢复记录，告警和运行手册               |
| P2     | 小范围业务扩展：评论或热卖推荐择一                    | 真实业务规则、权限、分页、风控和验收，不只多一个表 |

没有证据表明召回不足时不先换大Embedding；没有排序失败分布时不先上重排；没有复杂工具依赖时不扩Agent数量。模型能力和工程约束应分别测量。

## 阶段五：三次优化，暑期投递前形成完整作品

目标是一个可访问、可维护、可举证的公开演示。准备最小成本部署方案、演示账号数据隔离、资源配额、备份、异常回退与隐私说明；完成真实模型的多次回归、P50/P95延迟/成本、实际负载容量和故障恢复记录。只有观察到的数据才写简历。

容量测试需要写明硬件、实例数、模型并发、请求类型和数据规模。例如订单读取QPS、购买TPS、Agent任务排队和完成率是不同指标，不能混成一个“支持万级并发”。压测使用模拟模型和真实模型应分别报告，避免把桩性能冒称AI服务吞吐。

### 微服务什么时候值得做

有独立扩缩容需求、清晰服务边界和足够业务量时，优先考虑把耗时Agent worker或知识索引任务分离；交易核心仍可保持单体。只有评论/推荐等服务有独立发布或资源需求时才拆。拆之前先掌握模块化、契约和事务，拆之后补身份传播、消息一致性、可观测性、容错和发布成本。服务多不自动意味着必须微服务。

### 多模态如何贴合本业务

可以接“拍摄设备型号/指示灯/外观损坏→识别有限信息→用户确认型号与现象→检索排障/形成工单”。图片不是最终质量鉴定，不能凭照片自动退款或指导危险维修。需要图片隐私处理、存储访问控制、图像模型成本和专门评测集；当文字主链质量稳定且有真实需求时才引入。

## 暑期实习与秋招阶段

暑期投递前准备5分钟产品演示、10分钟核心设计、20分钟深入追问三种讲法。简历突出自己能证明的两至三项贡献，项目与实习互补。暑期中继续根据反馈修质量缺陷，不为了秋招临时堆一批不熟的技术。秋招前更新项目演进记录、真实数据和取舍，保留基线而非只展示最后截图。

## 每次优化的退出条件

开始前写清问题、基线、假设、改动范围、验收阈值和回退方法。结束时检查回归无退步、文档与代码一致、成本可接受、自己能解释源码。性能/质量没有改善时也记录无效实验；诚实的失败结论比编造提升百分比更能支撑深入讨论。

不要将个人作品命名为“已达到字节秋招级”或把路线当录用保证。最有说服力的是你能现场定位、修改、验证，并清楚知道下一步为什么做。

当前行动顺序：按[学习手册](项目学习实战手册.md)吃透→用[验收题](学习验收题与面试追问.md)找薄弱处→记录真实失败→选择下一轮最重要的2至3项。不要在同一周同时启动微服务、多模态、推荐和重排改造。
