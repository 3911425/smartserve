# SmartServe V2 项目学习实战手册

## 先说明学习目标

目标是让你能独立维护这个项目，接受后端/AI应用方向的深入追问，现场排查并修改一段真实逻辑。它覆盖项目能力，不能保证某家公司的面试、笔试或offer。算法、Java基础、计算机网络、操作系统、SQL与实习表现仍需单独训练。

读每章都执行“预测→看源码→调试→实验→讲解”。先写下自己的判断再运行，最后对照证据修正。不能只读这里的结论，也不能把模型生成的解释当成自己的能力。

建议为每一章建一页个人笔记，写：输入/输出、关键类与方法、状态写入位置、失败会怎样、一个自己复现的例子、一个尚未理解的问题。笔记可放项目`.local/study`，不会混入发布代码。

## 第1章：先把自己当客户与运营

先读[启动与账号](01-启动与账号.md)，使用离线方式，不消耗付费模型。注册自己的客户账号，观察初始余额10000；购买一件59元P1；查看待发货订单；问物流；登录管理员按客户找到它，模拟发货、签收；回到客户申请并确认退款；管理员批准；客户检查余额和流水。

第二次重复时换不同操作：待发货直接取消；先不确认退款，看管理员为何不能批准；管理员驳回；用demo历史订单申请，确认它为什么不增加余额。再提交一个工单，管理员认领、完成，回到原会话看人工回复。

产出：一张订单状态图、一张退款状态图、一张包含钱/库存/状态变化的表。验收时不看源码，逐步说明每一步由谁确认、是否已经写数据、能否撤回。把“询问政策”“建议”“创建申请”“确认”“批准”说成一件事，说明这一章还没过。

## 第3章：理解启动和配置优先级

先预测：`.env`是postgres-local，为什么全Docker可以用postgres？答案要落到Compose给后端设置的环境变量。再解释配置、进程、镜像、容器、卷分别是什么：配置是地址和开关；进程是正在运行的程序；镜像是运行环境和应用的模板；容器是基于镜像运行的隔离实例；卷保存容器生命周期之外的数据。

读`SmartServeApplication.main`，观察它怎样读取根目录`.env`且不覆盖已有环境变量；读`application.yml`的默认/demo、postgres-local、postgres段；读Compose的环境覆盖和端口映射。通过`/api/status`核实最终向量存储和模型开关，不能只凭文件推断。

实验：先本机启动，再停止，再混合启动，对比索引vectorStore；各自注册测试客户，观察不是同一个数据库。停止再启动确认订单还在。只删除容器而保留卷，说明为什么数据不依赖容器ID。不要执行`down -v`验证“会不会丢”，先理解命令再行动。

IDE调试时先停止脚本启动的后端，工作目录设为`backend`，运行`SmartServeApplication`。离线调试可在程序参数显式指定`--smartserve.llm-enabled=false`。数据库仍要明确配置；不确定时用隔离H2数据库并在日志确认连接URL，避免把故障实验放进自己的业务库。

验收：在白板标出浏览器5173→后端8080；混合方式后端→15432/16379/5672；容器方式后端→postgres:5432/redis:6379/rabbitmq:5672。能解释同一种服务为什么有两套端口和两套数据。

## 第4章：一次登录经过了什么

断点依次放在`AuthController.login`、`AuthService.login`、`Access.doFilterInternal`。用测试账号登录，观察数据库角色由服务器读取；随机会话token返回Cookie，表里只留下摘要；CSRF随响应返回，前端保存在内存。

下一次写请求，浏览器带Cookie，前端加CSRF头；过滤器验证会话并将Actor放到request属性，Controller不接受浏览器指定的真实用户ID。这里没有JWT，不需要为了回答面试把不相关的JWT结构背到项目上。

思考并写清：

- 密码熵低且需抵抗离线穷举，用有成本的BCrypt；会话token是高熵随机秘密，存SHA-256摘要便于查找和撤销。二者需求不同。
- HttpOnly阻止JS直接读取Cookie，不能独自防全部XSS；SameSite和CSRF/Origin检查共同限制跨站写入。Cookie不是“自动安全”。
- 改密码撤销全部会话，退出只撤销当前会话；环境初始化密码只用于创建账号，不是永久后门。
- 前端隐藏管理员入口不提供安全性；后端`Access.admin`与`Access.own`才执行身份和归属检查。

实验：不带Cookie读订单→401；带Cookie但缺CSRF写会话→403；客户调用管理员物流推进→403；注册请求夹带role=ADMIN仍只能建客户；修改密码后原会话失效。对应测试在`SmartServeIntegrationTest`中，先预测结果再运行针对方法的测试。

验收：能从浏览器一次请求追到过滤器、Actor和SQL，解释八次失败锁定的边界，以及为什么仍需公网反滥用/全局限流。

## 第5章：用59元购买讲清事务

断点顺序：`CommerceController.purchase`→`CommerceService.purchase`→`lockCustomer`→幂等查询→库存条件更新→钱包条件更新→订单/条目→ledger→event。

以余额10000、库存128、数量1为例：事务提交后余额9941、库存127、订单PAID、支付流水-59。若余额不足发生在库存已更新之后，抛运行时异常导致整笔回滚，库存也恢复；不能把方法里SQL执行先后误认为每条都已独立提交。

关键SQL不是“先查库存大于0，再更新”，而是：

```sql
UPDATE product_inventory
SET available = available - ?, version = version + 1
WHERE product_id = ? AND available >= ?;
```

检查影响行数为1才继续。钱包也用余额条件更新，另有数据库CHECK防线。客户行锁将同一人的余额操作串行化；不同客户买同一商品仍由库存行竞争保障。`@Transactional`作用在Spring代理调用边界，不能认为给private方法加注解就自动开新事务。

实验一：运行`checkoutDebitsWalletAndStockTogether`和`insufficientFundsRollBackInventory`，观察前后余额/库存。实验二：运行同键16并发测试，验证订单ID集合只有一个。实验三：运行不同客户竞争最后一件测试，观察“同用户锁”和“共享库存锁”的差异。

验收：不用说“加锁了所以安全”，而能指出锁住哪一行、什么时候释放、唯一约束哪一条、异常怎样回滚、吞异常会怎样。进一步说明单实例Java synchronized不能保护多个后端实例共享的数据库。

## 第6章：幂等键、请求哈希和流水约束

读`purchase`的request_key/request_hash、迁移文件的唯一约束、`ledger`的business_key。把网络超时拆成“事务没提交”和“已提交但响应没到”两种情况，分别解释客户端重试会发生什么。

同一个requestKey+相同输入返回原订单；同键改数量返回409。用户真正再买一次要生成新键。支付流水用`payment:订单号`，取消用`cancel:订单号`（以源码实际拼接为准），退款用`refund:订单号`，唯一约束是最后防线。幂等不等于不发生重试，也不等于所有接口有同一种实现。

数据库只读观察，在隔离PG库运行：

```sql
SELECT id,user_id,request_key,status,amount,funding_source FROM shop_order;
SELECT business_key,kind,order_id,amount,balance_after FROM wallet_ledger ORDER BY created_at;
SELECT product_id,available,version FROM product_inventory;
```

实验：同键换地址也应冲突，因为地址在请求哈希里。另开一次购买且用新键，应生成新订单。不要为了“修重复点击”把第二次合法购买永久拦截。

验收：能指出订单级幂等和资金流水级防重各保护哪种错误，说明没有分布式事务也能在本数据库内保证这次模拟购买原子性。

## 第7章：状态机和退款比一个按钮复杂

沿`advance`、`cancel`、`createRefund`、`confirmRefund`、`reviewRefund`读。画出客户、管理员、Agent三栏泳道，所有资金变化只能落在确定性服务方法里。

重点看：状态与version同时检查；退款窗口在创建和确认时重新检查，避免“刚刚能退”永久有效；管理员批准前验证待审核；终态重复返回原结果；恢复库存要明确标记；LEGACY_DEMO不能退成真钱包余额。

实验：先创建但不确认，管理员批准应409；确认后余额仍9941；并发批准后只回到10000；驳回不返钱，订单恢复原状态；历史订单批准也不加钱。解释为何当前系统每单只一份申请，驳回后的新材料为什么走人工单。

深入问题：如果将来接真实支付，数据库提交失败但支付机构已退款怎么办？当前本地事务不能跨供应商原子提交，需要支付请求幂等、回调验签、状态对账、补偿与异常单处理。先讲当前保证，再讲未来设计，不把未来设计说成已实现。

## 第8章：先看一条不用模型的客服路径

自己购买一笔订单，发送“查询订单 SS… 的物流”。断点：`ApiController.createRun`→`RunJournal.create`→`RunDispatcher.submit/consume`→`AgentOrchestrator.supervisor`→`order`→`McpBridge.call`→`McpController.rpc`→`ToolRegistry.call`→业务订单查询→`guardrail`→`RunJournal.finish`。

任务表先保存问题、身份、QUEUED，队列只得到runId。主管识别明确纯订单查询走确定性快捷路径，订单节点用工具查库、模板回答，不必调用远程模型。最后在Ops看modelCalls=0。BGE也不一定参与这条纯订单路径。

这说明“用了LangGraph4j”不等于每个节点都需模型。你应该能准确说：本项目以两个领域工具Agent为核心，搭配路由和确定性订单节点进行受控编排；订单节点并不是自主规划的订单Agent。

实验：用另一个账号的订单号问，工具拒绝，不能返回电话地址；不给订单号，先明确本人订单；历史出现多个不同订单，不能取最后一个当用户授权。

验收：把链路讲到“MQ放什么、worker从哪取正文、MCP发什么、哪个服务查哪张表”，不只说“主管交给订单Agent”。

## 第9章：再追一条原生工具调用循环

只在你明确开启模型且接受测试额度时做在线实验。也可先运行不收费的`ModelContractIntegrationTest`，它使用真实LangChain4j HTTP序列化与本地协议桩，不是真实 TokenDance 模型质量测试。

问题“S1门锁没电怎么开门”：主管常见调用一次得PRODUCT；领域Agent第一轮可能返回searchKnowledge工具请求；程序验证schema和白名单，经MCP实际检索；工具结果加入消息列表；第二轮模型组织答案；护栏可能再调一次模型核验。这条具体协议桩测试为4次，真实模型可能多查getProducts或先追问，次数由实际轨迹决定。

在`ModelGateway.step`看SDK响应`AiMessage`的toolExecutionRequests；在domain循环看`ToolExecutionResultMessage.from`怎样关联call_id。工具结果必须回给同一轮对话，不能只执行完把字符串随便拼到另一次请求里。JSON解析失败、重复参数、超预算都会回退，不无限循环。

实验：协议桩第一次503，再成功。预期model_call多一条ERROR，Token为空；随后成功用量照常记录。记录失败与重试，而不只计最终成功请求。对比“工具请求一次”和“HTTP模型请求一次”，两个数字通常不相同。

验收：能解释温度0也不等于所有输出恒定；工具schema限制形状但不能代替业务权限；模型审查不是事实真值；同系列模型评审存在偏差。

## 第10章：MCP不是一句工具注解

读`McpBridge.initialize/rpc/call`，对照`McpController.rpc`的switch和`ToolRegistry.definitions/specifications/call`。本项目先协商/发现目录，再tools/call，经HTTP传JSON-RPC。

画出两套凭证：浏览器Cookie证明登录客户；内部MCP服务token证明受信后端调用。身份头只能由受信后端提供，不能开放给任意外部客户端来指定“我是谁”。模型参数没有userId字段，恶意夹带会拒绝；订单工具强制按客户权限，不因admin模型提示提升。

实验：在测试中调用未发布的createRefundDraft，预期拒绝；PRODUCT调用订单工具拒绝；额外userId参数拒绝；订单输出不包含recipient/phone/address。说清请求被哪一层拒绝，而不是笼统“有权限控制”。

验收：能解释为什么同一个Java进程绕HTTP仍有教学价值，也能承认它增加序列化、网络等待和维护成本；如果未来服务拆分才会进一步体现独立部署价值。

## 第11章：RAG先学入库，再学查询

第一遍只读`KnowledgeService.run/reindex`，找出四份Markdown来源。选择“知温T1”一节，从标题、正文、切块offset到chunkId、content_hash、model_id、product_code、document_version逐个核对。

小例子：每块500字符，步长450，则第二块从450开始，与第一块重叠50字符。目的在于减少跨边界信息断裂，但仍不是语义完美分块。标题帮助来源解释和检索，内容hash帮助决定是否复算，模型ID防止换模型后混用不同空间向量。

BGE输出512个float，是一段文本的语义表示。H2/普通PG把数组作为JSON文字保存也能恢复成float[]，JVM再计算余弦；pgvector另存成vector(512)，数据库执行距离TopK。保存方式、计算位置、模型来源是三个不同问题。

实验：在隔离资料副本改一句，重新索引，检查revision变化；再次不改资料重索引，确认复用条件；设想换模型为什么不能只改一个模型名。不要修改生产依赖版本来“验证维度”，先用单元实验。

验收：能说出空向量/维度不符时余弦返回什么，向量归一化与余弦的关系，且知道当前BGE512维不是自己训练出的成果。

## 第12章：把一次检索拆成候选、排序、门槛

第二遍读`search`。问题“T1用什么电池”：识别T1产品范围→问题BGE向量→dense候选→中文二元词BM25候选→取并集→融合排序→Top5→accepted判断→Agent只消费accepted。

手算一组余弦、BM25词频和RRF名次贡献，不要求背整套数学推导，但要知道分数越大意味着什么。BM25的TF、IDF和长度归一化分别修正什么；缺失名次为什么贡献0；权重为什么必须用数据校准。

本次实际缺陷可作为案例：旧正则使用英文单词边界识别T1，中文紧跟后面使边界不成立，导致领域门槛/范围过滤漏判；修复为限制前后ASCII字母数字，并补回归。它不是“Embedding模型太弱”，换更大模型并不能修复错误的业务正则。

另一类失败：相关证据在Top5但accepted=false。要分别检查domainQuery、semanticScore、lexicalScore。没有区分召回率和可用证据覆盖率时，你会错误认为Recall高就一定能回答。再比较BM25、vector、hybrid的MRR；混合不一定每项更好，报告数据不支持就不宣称提升。

实验：运行`node scripts/evaluate-retrieval.mjs`（先启动隔离评测服务），选择一个真实失败，写下预期标题、实际候选、门槛原因、修复假设和回归结果。不能只挑三个好例子截图。

验收：能指出当前是非神经融合，没有真实Cross-Encoder；语料小、中文二元词简单、通用FAQ可能跨型号、索引非原子发布等限制。

## 第13章：Redis缓存应该缓存什么

读`search`的cacheKey和15分钟TTL。键包含revision、strategy、queryHash、limit，知识内容/模型/策略变化通过revision隔离旧结果。缓存命中跳过本次BGE查询和排序，未命中计算后写回。

这里没有把订单、钱包、库存放Redis，因此不需要拿余额缓存双写一致性来描述当前实现。缓存失败回源，不影响资金正确性。它减少重复检索代价，但不能自动解决模型并发和数据库交易吞吐。

混合模式实验：同问题检索两次，观察结果一致并检查对应键；更新知识后revision变化，旧键还在但不再命中；停项目Redis，检索应回源。记录耗时前先说明冷/热模型、样本数和机器，不凭一次快慢编写提升百分比。

验收：说明缓存穿透、击穿、雪崩在此类小项目中是否已处理。当前没有请求合并、分布式锁或随机TTL策略，不要把知道概念说成已实现。

## 第14章：RabbitMQ、持久任务、租约和恢复

先画时间线：创建任务事务提交→MQ投递→CAS领取→90秒租约→10秒心跳→节点检查点→最终提交。任务5秒恢复扫描、最多3次领取。消息只含runId，所以正文不会因消息重复而变成多份独立任务。

然后按问题学习：

- 数据库提交后、投递前进程死了：QUEUED仍在，恢复扫描补投。这是任务表兼任投递清单，不是已实现通用Outbox基础设施。
- MQ重复投递：只有一次CAS领取成功；其他消费者看到非QUEUED就退出。
- worker死在外部模型请求后：租约过期重新执行，模型请求可能重复计费，没有外部恰好一次保证。
- 旧worker恢复：ExecutionScope校验租约，旧token不能写检查点或最终答案。
- 取消：撤销租约、状态CANCELLED；不能撤销已经传给供应商的HTTP请求。

读`JdbcCheckpointSaver`如何序列化图状态。区别“保存下一节点”与“保存领域循环里每次工具请求”；本版本只有前者，因此恢复粒度有限。`ThreadLocal`在当前顺序图执行中传递租约，未来改成异步线程/并行节点必须显式传播上下文，不能直接照搬。

实验：在隔离服务中取消任务，验证旧租约不能finish；人工制造旧租约token执行checkpoint保存，测试应拒绝；实例重启后查看持久检查点。停止MQ的演练只影响项目容器，不操作你原有Redis或系统PG。

验收：能够承认DLQ已声明但业务失败主要由持久任务状态处理，不是完整人工重试后台；重投、重试、恢复、取消分别是什么。

## 第15章：SSE与AgentOps到底看什么

读后端`stream`和前端`streamRun`。服务端周期读取run_event，自增事件ID作为游标；客户端断线携带Last-Event-ID，补读后再读取最终任务。SSE是一条服务器到浏览器的流，业务请求仍通过普通HTTP。当前没有逐token模型流式输出，页面显示的是阶段事件和最终答案。

Ops里选一个任务，对照routing/tool/retrieval/model/validation/completed事件和model_call表。把每条model用途写成中文：路由、领域第几轮、护栏、重试。汇总Token是已知响应统计，失败未知不能当免费。

LangSmith是可选脱敏远程导出，不能替代本地业务审计或评测。没有实际导出成功记录时不宣称远程链路已验收；没有错误分析时也不能说“接了LangSmith所以回答可靠”。

实验：SSE断线后续读不应重建run；取消后界面回到可输入；客户不能读另一个用户run；反馈只能写已完成的本人回答。观察人工复核怎样从失败案例进入知识维护，而不自动污染知识。

## 第16章：建立能经得起追问的评测习惯

先读[评测与验证报告](06-评测与验证报告.md)。检索集72例、任务集32例是固定回归资料，不是生产流量、不是官方面试题、也不是独立专家盲测。`regression/challenge`当前开发可见，不能包装成真正未见过保留集。

三层指标分别回答：

| 层级      | 主要问题                        | 当前方法                                        |
| --------- | ------------------------------- | ----------------------------------------------- |
| 检索      | 找到相关片段了吗，是否过度接受  | Recall@5、MRR@5、accepted相关覆盖、负例误接受   |
| Agent任务 | 路由/工具/确认/权限是否满足目标 | 固定业务夹具、API结果、资金与申请数量不变等断言 |
| 答案      | 事实有无支持、是否解决问题      | 参考要求+自定义模型评审+人工抽查                |

Recall例子：一题标两个相关标题，只命中一个，单题Recall=0.5；MRR若第2名首次相关则0.5。accepted覆盖不是对所有片段的precision，负例误接受也不是所有幻觉率。关键词包含不能覆盖完整语义，规则通过不代表任务真正解决。

实验报告模板：问题和假设、数据来源和标签、样本分组、环境及知识revision、基线、改动、指标、失败列表、成本/延迟、人工抽查、限制、结论。只改一个主要变量，保留基线。没有显著提升时如实写“未证明更优”。

当前自定义judge不叫RAGAS。它直接发送已保存的问题、回答、证据和参考要求，付费调用单独统计；同系列模型评分偏差和标注不完整都要说明。后续接RAGAS等库可以复用数据契约，但不能把安装库等同于评测体系。

验收：别人问“你98%的指标怎么来的”，你能打开原始结果、讲分母、相关性标签、是否开发可见、失败案例及可重复命令。不能说“模型感觉回答不错”。

## 第17章：独立修改一次，证明你会维护

从下面择一，先自己写设计，不让AI直接替你生成全部实现：

1. 为工单幂等加入请求哈希，同键改表单返回409，保留已有数据迁移策略。
2. 为单个检索结果增加拒绝原因字段，前端展示，并补有意义的门槛回归。
3. 为管理员退款列表加分页，同时检查过滤和权限，不能只切前端数组。
4. 给真实模型耗时增加按节点分组的P50/P95统计，说明样本不足时不显示误导百分位。

每个任务都交付：需求边界、涉及文件、数据库变化、失败场景、必要测试、前后效果、未解决问题。能提交一个小而正确的修改，比背完所有框架类名更有价值。不要在学习实验时未经核验把改动混到主运行数据里。

## 第18章：补齐Java与后端基本功

项目相关重点：集合/泛型与不可变集合，BigDecimal构造/精度，异常与事务回滚，线程池队列与拒绝策略，CAS条件更新、ThreadLocal传播和清理，Spring代理/自调用/依赖注入，SQL索引和锁，Cookie/同源/CSRF，HTTP超时和重试，JVM内存与ONNX本地内存。

把每个概念关联到一处真实代码。例如：有界队列满时任务留QUEUED；ThreadLocal用try-with-resources清理；CGLIB代理不能靠直接读被代理对象public字段拿依赖，所以外部使用service getter；构造BigDecimal不使用double；读写事务不包住长时间模型HTTP请求。

算法训练另开固定时段：数组/哈希、双指针、滑窗、二分、链表、栈队列、树、图、堆、动态规划，先实现常见基础，再做限时题与复盘。SQL练连接、分组、窗口函数和索引解释。项目手册不包含某公司完整笔试范围，不能替代这些训练。

## 最终验收：不用文档讲、现场查、亲手改

准备三份自己写的材料：一张整体架构图、一张订单/客服两条详细时序图、一页真实评测与失败复盘。用5分钟演示产品，10分钟解释最有价值的两个设计，20分钟接受追问，再用30至60分钟现场完成一个小修改并验证。

按[验收题与面试追问](学习验收题与面试追问.md)打分。发现薄弱环节回到对应源码和实验，先补正确性，再追深度。能诚实、精确、可复现地回答“做了什么、为什么、如何证明、哪里还不够”，才是这一轮学习应达到的项目能力。
